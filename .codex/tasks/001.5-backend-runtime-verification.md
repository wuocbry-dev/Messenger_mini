# Task — Backend Runtime Verification and Maven Wrapper

## Objective

Verify that the Messenger Mini backend actually builds and starts
successfully against the existing MySQL database after the Flyway
baseline task.

This is a verification/foundation task.

DO NOT implement Authentication, Chat, Conversation, File, R2, Agora,
or any other business feature in this task.

Read first:

- /AGENTS.md
- /backend/AGENTS.md
- /docs/ARCHITECTURE.md
- /docs/DATABASE.md
- /docs/DECISIONS.md
- /.codex/tasks/001-flyway-baseline.md

Inspect the existing repository before changing anything.

==================================================
1. IMPORTANT CURRENT STATE
==================================================

The existing development database has already been baselined.

Expected Flyway state:

flyway_schema_history:
- version = 1
- type = BASELINE
- description = Existing Messenger Mini schema
- success = 1

The approved application tables are:

- users
- refresh_tokens
- conversations
- conversation_members
- messages
- message_receipts
- stored_files
- message_attachments
- calls

DO NOT:

- drop the database
- drop application tables
- delete existing rows
- recreate existing tables
- rerun V1 against the baselined database
- change the baseline version
- use Hibernate schema generation
- use ddl-auto=update
- use ddl-auto=create
- use ddl-auto=create-drop

Keep:

spring.jpa.hibernate.ddl-auto=validate

==================================================
2. VERIFY JAVA ENVIRONMENT
==================================================

Inspect:

backend/pom.xml

Determine the exact required Java version from the project.

Run and report:

java -version
javac -version

Do not silently change the Java version in pom.xml merely because
the current machine has a different JDK.

If the required JDK is unavailable, clearly report the mismatch.

==================================================
3. ADD MAVEN WRAPPER
==================================================

The repository currently has no Maven wrapper and the environment
previously reported:

mvn -v -> spawn mvn ENOENT

Add the official Maven Wrapper to the backend project so contributors
do not need a globally installed Maven installation.

Expected backend files should include, as appropriate:

backend/mvnw
backend/mvnw.cmd
backend/.mvn/wrapper/maven-wrapper.properties

Use an official/reproducible Maven Wrapper setup.

Do NOT create fake wrapper scripts that only pretend Maven exists.

Choose a Maven version compatible with the current Spring Boot project.

After adding it, verify the wrapper itself.

On Windows prefer:

backend\\mvnw.cmd -v

On Unix-like environments:

./backend/mvnw -v

Report the actual Maven version used.

==================================================
4. VERIFY DATABASE CONNECTION TARGET
==================================================

Before running any application verification, determine exactly which
database the backend configuration connects to.

Report without exposing passwords:

- DB host
- DB port
- DB name
- JDBC URL with credentials removed
- active Spring profile

Expected DB name:

messenger_mini

Execute safe/read-only checks to confirm the target database:

SELECT DATABASE();

SELECT COUNT(*) FROM users;
SELECT COUNT(*) FROM refresh_tokens;
SELECT COUNT(*) FROM conversations;
SELECT COUNT(*) FROM conversation_members;
SELECT COUNT(*) FROM messages;
SELECT COUNT(*) FROM message_receipts;
SELECT COUNT(*) FROM stored_files;
SELECT COUNT(*) FROM message_attachments;
SELECT COUNT(*) FROM calls;

Also inspect:

SELECT installed_rank,
       version,
       description,
       type,
       success
FROM flyway_schema_history
ORDER BY installed_rank;

IMPORTANT:

A previous verification reported 0 rows in every application table.

If the current user expected test data to already exist but all row
counts are still zero:

DO NOT insert replacement data automatically.

Instead report clearly that the backend appears to be connected to a
database/schema with no application data and provide the exact
non-secret connection target so the user can compare it with MySQL
Workbench.

Do not guess.

==================================================
5. VERIFY FLYWAY
==================================================

Verify that:

- Flyway starts successfully.
- Existing baseline version 1 is recognized.
- V1__initial_schema.sql is NOT executed against the existing
  baselined database.
- No pending migration unexpectedly modifies the schema.
- flyway_schema_history remains valid.
- Existing data counts remain unchanged before and after startup.

Do not enable permanent baseline-on-migrate.

==================================================
6. VERIFY JPA / HIBERNATE MAPPING
==================================================

Start Spring Boot against the development MySQL database.

Hibernate must run with:

ddl-auto=validate

Verify mappings for all existing entities:

auth/entity/RefreshToken
user/entity/User
conversation/entity/Conversation
conversation/entity/ConversationMember
message/entity/Message
message/entity/MessageReceipt
message/entity/MessageAttachment
file/entity/StoredFile
call/entity/Call

Also verify embedded/composite IDs:

ConversationMemberId
MessageReceiptId

Fix mapping problems ONLY if they are actual mismatches between the
approved MySQL schema and the JPA model.

Do not alter the approved schema just to make an incorrect entity pass.

If a mismatch exists:

1. determine whether migration or entity is wrong,
2. compare with docs/DATABASE.md and V1__initial_schema.sql,
3. preserve the approved database contract,
4. make the smallest correct fix.

==================================================
7. VERIFY SPRING BOOT STARTUP
==================================================

Start the application.

Confirm:

- Spring context starts.
- datasource initializes.
- Flyway succeeds.
- Hibernate validate succeeds.
- SecurityConfig does not prevent application startup.
- WebSocket configuration does not prevent startup.
- OpenAPI configuration does not prevent startup.
- R2 placeholder configuration does not require real R2 credentials
  merely to start local development unless intentionally designed so.
- Agora placeholder configuration does not require real Agora
  credentials merely to start local development unless intentionally
  designed so.

External services should not block basic backend startup at this stage.

Do NOT implement fake R2 or fake Agora services.

==================================================
8. VERIFY SPRINGDOC / SWAGGER
==================================================

Once Spring Boot starts, verify the existing springdoc setup.

Check that the OpenAPI endpoint is reachable, typically:

/v3/api-docs

and Swagger UI is reachable using the configured springdoc path.

Expected API title:

Messenger Mini API

Expected API version:

v1

There may be no business endpoints yet.
That is acceptable.

Do not invent endpoints just to populate Swagger.
